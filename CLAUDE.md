# Hive Local — project notes

A Home Assistant Marketplace (formerly HACS) custom integration, domain `hive_local`, for local control of Hive receivers on Zigbee2MQTT or ZHA. It adds a **Hive** sidebar panel with tabs, in the style of the Wiser integration, plus boost/mode entities and actions. Built for Elliot's own Hive setup. Local-first and no cloud.

Don't use the domain `hive`: HA core's cloud Hive integration already has it, and a custom integration with the same domain would override it.

## Layout

- `custom_components/hive_local/`
  - `__init__.py`: `async_setup` registers the static path, websocket commands and services once. `async_setup_entry` builds the transport, stores `HiveData` in `entry.runtime_data`, forwards the platforms and registers the panel. The panel is removed when the last entry unloads.
  - `config_flow.py`: a menu (`z2m` | `zha`), stored as `transport` (entries without it are Z2M). Z2M: base topic, then a dropdown of Hive receivers read from Z2M's retained `bridge/devices`; multi-endpoint climate exposes → `slr2`. ZHA: a `DeviceSelector(integration="zha")`; Thermostat clusters on endpoints 5 and 6 → `slr2`, unique id `zha:<ieee>`, stores `device_id`. Both store the receiver's model in `z2m_model` (e.g. `SLR1c`), despite the name.
  - `transports/`: `base.Transport` (per-channel status, resume-after-boost, default manual setpoint), `z2m.Z2MTransport` (all MQTT) and `zha.ZHATransport` (zigpy). Z2M subscribes to `<base>/<name>`, sends a `/get` refresh on start, and polls the hold duration every 60 s while boosting. ZHA is described under Key facts. `base.Transport` also keeps a boost deadline (from our own boost, else the first valid reported duration): if the receiver is still boosting `BOOST_DEADLINE_GRACE` after it, we cancel the boost (back to the pre-boost mode), and when the receiver reports no duration the time left comes from the deadline. Z2M can replace the duration with null/65535 and the receiver then boosts indefinitely (reported by the HomeDash fork of Hive Local Thermostat). Deadlines and the pre-boost mode are saved in `.storage/hive_local.boost.<entry_id>` (`boosts.py`, pure; #18): `async_load_boosts` runs before `async_start`, the timer restarts once the receiver reports it's still boosting (cancelling at once if the deadline is long gone; a valid reported time left that runs later wins, since that's a new boost started while HA was down), and any non-boost report drops it. Unloading keeps them; removing the entry deletes the file. Status changes fire `SIGNAL_STATUS` and `f"{SIGNAL_STATUS}_{entry_id}"`.
  - `transports/zha.py` is imported lazily, only for ZHA entries, so Z2M installs never import zigpy. `mqtt` and `zha` are `after_dependencies`, not `dependencies`.
  - `data.py`: `HiveData` (transport + per-channel boost defaults); `HiveConfigEntry`.
  - `climate.py` (heating: auto = schedule, heat = manual hold, off; boost is a preset; schedule "off" periods (1 °C) show the HA-side frost protection number (default 12 °C, display only, like Hive Local Thermostat) so the target stays adjustable; no target when off; setting a temperature on auto sends only `occupied_heating_setpoint` (override until the next scheduled change, as Hive Local Thermostat did; **unverified** on Elliot's receiver), mid-boost re-boosts keeping the time left, and on heat changes the hold), `water_heater.py` (hot water: schedule/on/off/boost, no temperatures) and `entity.py` + `select.py` (mode), `sensor.py` (boost remaining), `number.py` (boost duration/temperature and heating frost protection, restored, stored in HA only) and `button.py` (boost/cancel).
  - `services.py` / `services.yaml`: `boost_heating`, `boost_water`, `cancel_boost_heating`, `cancel_boost_water`, `set_holiday` (`until`, `temperature?`), `cancel_holiday`. `device_id` is optional when there's only one receiver; the holiday actions cover every receiver without it.
  - `diagnostics.py` (#12): "Download diagnostics" on the entry: redacted entry data, the transport's `diagnostics()` (status, boost deadlines and resume modes, the last schedule read with the receiver's raw replies; Z2M adds the last state message; ZHA adds endpoints and clusters, the Thermostat attributes, the SLT reporting state with shortened IEEEs, and zigpy/zha versions), boost defaults, pre-heat, our entities' states and the receiver's rooms. `.github/ISSUE_TEMPLATE/bug_report.md` asks for it. Diagnostics also carry the transport's `started` / `last_seen` and the kinds of Repairs issue raised.
  - Repairs (#13): `problems.py` (pure, tested) decides, `health.py` raises and clears issues in HA's issue registry (not persistent, so a restart starts clean; each clears itself when the problem goes away; unloading an entry clears its own). `ReceiverHealth` per entry (`HiveData.health`), every minute: `receiver_silent` (nothing from the receiver for 30 min; `Transport.last_seen` is set by any Z2M message on its topic or any ZHA report/read answer, not by the cache at start, and after 10 quiet minutes `async_ping` asks again: Z2M sends `/get`, ZHA already re-reads every 5 min), `z2m_no_state` (Z2M, nothing at all 5 min after start: a wrong friendly name or base topic; shows the topic), `zha_device_lost` (ZHA hasn't had the device for 5 min; fixable: `repairs.py` reloads the entry) and `thermostat_quiet_<ieee>` (a Hive SLT we watch hasn't reported temperature for 15 min once it took our reporting, 35 min before). **ZHA reloads are handled:** `ZHATransport.check_device()` (every minute) looks the receiver up again and, when ZHA has new cluster objects, moves our listeners over to them, restarts the thermostat watcher and re-reads the state; silence then counts from the reconnect. `ValveHealth` (house-wide, `hass.data[DATA_VALVE_HEALTH]`, every 5 min, from `RoomManager.valves()`): `valve_battery_low_<entity>` (≤ `rooms.LOW_BATTERY`) and `valve_unavailable_<entity>` (unavailable for 30 min). Strings are under `issues` in `strings.json`. `tests/e2e/test_health_e2e.py` covers all of them.
  - `websocket.py`: `hive_local/devices|subscribe|get|set|mode|boost|cancel_boost|target|preheat|defaults|stats|settings|settings/set|holiday/set|holiday/cancel` (the holiday ones take an optional entry_id: every receiver without it), plus `hive_local/rooms/subscribe|candidates|valves|suggest|identify|save|delete|set_target|mode|stats|boost|cancel_boost|schedule/get|schedule/set`. **No writes while reading (Elliot, 2026-11-26):** `hive_local/get` and `rooms/schedule/get` mark that schedule as being read (`_reading`, a count per `("receiver", entry_id, channel)` / `("room", room_id)` in `hass.data`), and `hive_local/set`, `rooms/schedule/set` and `rooms/mode` to Schedule for it are refused with error code `busy` until it's over; in the panel, `ScheduleEditor` disables the slots, Add a time, Undo, Save and the Copy items while reading, and `ScheduleSource.onReading` tells a page about the read. `tests/e2e/test_schedule_busy_e2e.py`. `defaults {entry_id, channel, boost_minutes?, boost_temperature?, frost_temperature?}` goes through the number entities (unique ids `<entry>_<channel>_boost_minutes|boost_temperature|frost_temperature`), like `preheat`, so they're restored.
  - `settings.py` (0.9.0): `HouseSettings` in `hass.data[DATA_SETTINGS]`, created in `async_setup`, stored in `.storage/hive_local.settings`. Holds the house-wide `outdoor_entity` (a `weather` entity or a temperature `sensor`, not one of ours); `outdoor_candidates()` lists them, weather first. Also (issue #11) the boiler's average output while on and the gas price. **Output:** the receiver calling for heat isn't the boiler burning flat out (Elliot's 24 kW OTR1 boiler averaged ~9 kW: Hive Local said £11.82 for a day Octopus billed £4.68, 2026-11-24), so a `gas_meter` (a statistic id: the Energy dashboard's gas source or a gas sensor, `gas_meter_candidates()`) is fitted with `cost.fit_output` (pure, tested): the last 14 complete local days' gas kWh (`history.async_gas_per_day`, recorder daily statistics `change`, volumes → kWh) against hours any receiver's heating was on (`cost.heating_intervals`/`merge`/`hours_per_day`), gas = baseline + kW × hours by least squares (≥ 4 days, ≥ 3 h, ≥ 1.5 h spread, else through zero); learned 120 s after start, every 6 h and when the meter changes, stored as `fit`. Without a meter, `boiler_kw` (the rating) × `cost.MODULATION` (0.4). `output_kw()` → (kW, "meter"|"rated"). Then `price_source` = `"energy"` (HA's energy settings: the first gas source's `entity_energy_price` or `number_energy_price`, per the gas meter's unit; `energy` is an `after_dependency`), `"fixed"` (`fixed_price`, per kWh in the main currency; the panel calls it **Unit rate** and shows its own row under Gas price with a − / + stepper in pence/cents, 0.01 a tap, held to repeat and then 0.1 at a time, chosen by Elliot 2026-11-24 over a typed box) or a price entity (`price_candidates()`: sensor/number/input_number with a unit like `GBP/kWh` or `GBP/m³`). `cost.py` (pure, tested) reads price units (kWh, MWh, m³ at `KWH_PER_M3` 11.2, ft³, CCF; p/c = hundredths). `async_cost()` gives `{boiler_kw, price, per_hour, currency, source}`, which `hive_local/stats` returns as `cost` for heating (null for water, or until both are set); the panel multiplies the boiler's minutes by `per_hour`, at today's price. Stats has a third toggle (cash icon) only once it's set up, labelled an estimate (a modulating boiler rarely runs flat out); Settings has a Heating cost section.
  - `rooms.py` (pure, unit-tested): validate a room, and summarise its valves (room temperature from the sensor or the valves' average, one target or the spread, heating, lowest battery). A valve counts as heating only while the room is below that valve's target (`_heating`; a valve turned down keeps saying heating while it closes, which showed "Heating to 6.5°" in a warm room: Elliot, 2026-11-26), the same rule as rooms calling for heat. `room_manager.py`: `RoomManager` per receiver (`HiveData.rooms`). It stores rooms in `.storage/hive_local.rooms.<entry_id>`, offers only Hive valves (`rooms.is_hive_valve`: device model or model_id contains TRV001/TRV003 on ZHA, where the manufacturer reads "Danfoss", or UK7004240 on Z2M), uses their HA climate entities, finds each valve's battery sensor on the same device, and sets targets with `climate.set_temperature`. `frontend/src/Rooms.tsx` has the room pop-up (`RoomSheet`), the editor (`RoomEditor`/`RoomEditorDialog`, a dialog) and `RoomSetupDialog`; there's no Rooms tab since 0.9.0 (see Panel structure). `rooms.suggest_rooms` (pure, tested) + `RoomManager.suggestions()` give a room per HA area with Hive valves not in a room (the area's first temperature sensor not on a valve device); `RoomManager.async_identify` presses the valve device's `button` with device_class identify (ZHA creates one; Z2M only if it exposes identify), and `_valve()` carries `identify: bool`. Rooms take **one** sensor; several (averaged) is issue #23, for a later release. The sensor's reading is pushed into each valve (#3, `valve_sensor.py` / `valve_sensor_controller.py`, opt-out per room with `sensor_on_valves`; see the rooms roadmap, step 2). Rooms are **house-wide** (0.3.2): one `RoomManager` in `hass.data[DATA_ROOMS]`, created in `async_setup`, stored in `.storage/hive_local.rooms`. Each room has a `receiver` (entry_id, its heating zone), set automatically with one receiver and required with several. On first start it imports 0.3.0/0.3.1's per-receiver stores (`hive_local.rooms.<entry_id>`) and removes them. The room websocket commands take no entry_id.
  - Valve schedules (#5; **works on a real Hive valve**, Elliot tested it on 2026-11-26, so the Experimental chip and "not yet tried" note are gone): a room's weekly schedule kept on each of its Hive valves (a Danfoss Ally keeps 6 transitions a day, endpoint 1, the receiver's ZCL commands) and followed only in its "schedule" programming mode. `trv.py` (pure, tested in `test_trv.py`): valve address from the device registry identifiers (`("zha", ieee)` / `("mqtt", "zigbee2mqtt_0x…")`), Z2M's `schedule_<day>` text ("06:00/21 22:00/17"), `combine_reads` (the first valve with the most days; `differs` lists days the valves disagree on), and the clock: ZCL time is seconds since 2000-01-01 UTC, `time_attributes` (time, time_status 0x02, standard `time_zone`, `dst_start/end/shift` from the HA time zone, either hemisphere), `clock_offset` (the valve's `local_time`, else time + zone + DST, against HA's local time) and `CLOCK_TOLERANCE` 120 s. Valve setpoints are 5–32 °C. The editor's "Off" is the room's receiver's **frost protection** (`RoomManager.frost`, Settings → Frost protection, default 12 °C; Elliot, 2026-11-26, "like the receiver"), returned as `limits.frost` by `rooms/schedule/get`: the Ally has no off, so what Off writes is what it holds. Slots at that temperature, or at 5 °C or below (older writes), show as Off; on a read, `RoomSchedule` turns 5 °C-or-below slots into the frost temperature as unsaved changes (`ScheduleSource.read` may return `edited` + `note`), so one Save moves valves written before the change (Elliot saw them still at 5, 2026-11-26). Harness: `?oldoff=1`. `valve_schedule.py`: `async_read_room` (every valve at once; `VALVE_READ_TIMEOUT` 15 s, it sleeps), `async_write_room` (validated, then every valve, one command per day with only its own transitions, `schedule.per_day(pad=False)`: Z2M sends the Ally exactly its transitions, and padding to 6 repeats a time, which the valve may refuse (Elliot's read/save gave `Status.FAILURE: 1`, 2026-11-26; the receivers keep their padding); the panel sends only changed days; partial failures come back in `failed`, all failing is an error) and `async_set_room_schedule_mode`. **ZHA** (`transports/zha_valve.py`, lazily imported): the read/write share `read_weekly_schedule` / `write_weekly_schedule` with the receiver (`transports/zha.py`; reads `expect_reply=False` + legacy listener), but valve writes wait for the default response (Z2M doesn't disable it for the Ally). **Sleepy:** every valve request (schedule read/write, clock, schedule mode) goes through `zha.send_when_awake`, which tries again every 5 s for up to `VALVE_WAKE_WAIT` (120 s) while delivery fails (the parent drops a message the sleeping valve doesn't poll for; Z2M queues them instead); the panel says pressing a valve's dial wakes it. **Clock:** before writing, each valve's Time cluster (0x000A) is read and, if more than 2 min out or unset, set (like Z2M does daily for the Ally) and read back; still wrong (or refused) skips that valve ("Not written, its clock may be wrong"). Reads only report it. Chosen over refusing: the Ally needs the right time for any schedule, and ZHA's Danfoss quirk only writes the time when binding, with no DST (an hour out all summer in the UK). `programing_oper_mode` bit 0 = follow the schedule. **Z2M:** supported: zigbee-herdsman-converters' Ally definition (`danfossWeeklySchedule`) has `schedule_<day>` keys (one setWeeklySchedule / getWeeklySchedule per key, queued for the sleepy valve) and sets the clock itself (on pairing, rejoin and daily), so we don't check it; the valve's topic is `<base>/<friendly name>` found by IEEE in `bridge/devices` (each Z2M receiver's base topic, then `zigbee2mqtt`); a read takes `schedule_<day>` and `programming_operation_mode` from state messages after the `/get` (Z2M's state carries its cache, so a stale day is possible). Websocket `hive_local/rooms/schedule/get|set`; the valves' schedule mode is switched by the room's mode (`rooms/mode`; the separate `rooms/schedule/mode` was removed, Elliot 2026-11-26). Panel: the room page's Schedule tab → `RoomSchedule.tsx` (`RoomScheduleDialog`, on the room page with `page`: the status line from the room's mode, like the heating's ("Your schedule is running" / "isn't being used: the room is on Manual"; the old "The valves follow this schedule · Use it / Stop" row duplicated the Control tab's Schedule / Manual / Off and is gone, Elliot 2026-11-26), notes on clocks, missing days, disagreements and valves not following it, and the sleep hint below) around `ScheduleEditor` with a `source` (read/write/noun/statusLine; `embedded` makes the ⋯ button and save bar sticky in the dialog). `tests/e2e/test_valve_schedule_e2e.py`: a real zigpy device with Thermostat + Time on endpoint 1 and a fake Ally radio (per-day replies, default responses, a clock an hour behind in BST), a clock that can't be set, and a room with a ZHA and a Z2M valve. Still unverified: the Z2M keys' behaviour on a real Z2M, and the valve's `local_time`.
  - `stats.py` (pure, unit-tested): `sample_from_state` turns a recorded state of our climate / water_heater entity into a `Sample` (mode, heating, current, target), and `summarise` gives heating minutes, cycles (off→on inside the period), boosts, time per mode, time-weighted temperatures, per-day totals, chart buckets (15 min / 1 h / 6 h for 1 / 7 / 30 days) and the same stretch of the previous period. `websocket.hive_local/stats {entry_id, channel, days, offset}` (offset = periods back) finds our entity by unique id and reads `recorder.history.get_significant_states(significant_changes_only=False)` (attribute changes matter: `hvac_action`, `heating`). Periods start at local midnight. `recorder` is an `after_dependency`. `frontend/src/Stats.tsx` is the Stats tab, laid out after the Hive app's Heating History (which Elliot shared): receiver tabs (several receivers; on a device page it's fixed to that channel), D / W / M and time or temperature (heating) toggles (Hive's £ cost isn't possible: no energy prices), a ‹ date › pill to step back, a tinted summary box with two numbers, a note (vs the period before, fired up, boosts), then a row per day (per hour on D, from the 15-min buckets) newest first: bar, value, and that day's low · high room temperature (where Hive shows the weather). Days carry `temp_min` / `temp_max`. The old SVG charts are gone. Not yet tried against real recorder data. **Outdoor temperature** (0.9.0, issue #10): the house-wide `HouseSettings.outdoor_entity` (Settings tab; it was briefly a per-receiver options flow, removed before release); `history.async_outdoor` reads its recorded history (weather: the `temperature` attribute; converted to HA's unit system) as `stats.Reading`s, and `summarise(outdoor=...)` adds `outdoor` {avg, min, max} to the period, `outdoor_avg` to `previous`, `outdoor_avg/min/max` to days and `outdoor` to buckets (all absent/None without a source). The panel shows an Outside column (low–high) on the rows and "6° outside, 3° colder than the period before" in the note, heating only; without a source it shows a one-line hint pointing to the Settings tab. `hive_local/stats` returns `outdoor_entity`.
  - Pre-heat (0.8.0, issue #8): `preheat.py` (pure, unit-tested) has `learn_rate` (warm-ups from recorded `stats.Sample`s: boiler on ≥ 20 min starting ≥ 1 °C below target, rise ≥ 0.3 °C, rate to the peak; the median once there are 3) and `plan` (only the very next scheduled change, only if it's a rise from what the schedule holds now; lead = climb / rate + 10 min, capped by max lead). `preheat_controller.Preheat` (`HiveData.preheat`, heating only): opt-in via `switch.py` (restored), max lead via `number.PreheatMaxLead` (default 120, 15–240), learns from 14 days of history 60 s after start and every 6 h (`history.py`, shared with Stats), and keeps the heating schedule in `.storage/hive_local.schedule.<entry_id>` from every panel read/write (`schedule_seen`), reads it when enabled without a full week, and re-reads it nightly at 03:17. Every minute, on Schedule, it **boosts** to the new temperature until the scheduled time (self-expiring, so it fails safe; chosen over a setpoint override, which is unverified). Someone cancelling our boost (Stop pre-heating, Manual, Off) skips that change (the card says so) until the heating goes from Manual or Off back to Schedule, or pre-heat is turned on again; choosing Schedule while pre-heating does nothing (`HiveData.async_set_mode`), since the pre-heat is the schedule, and the panel shows Schedule selected. Turning pre-heat off mid-way cancels it. A schedule read or write checks a running pre-heat (`preheat.still_wanted`): if the change it was for is gone (moved, removed or off) the boost is cancelled at once and it re-plans; if only the temperature changed it boosts to that instead, to the same end. Mode changes are acted on at once, not on the next minute. The running pre-heat (`active_for`) is saved in the same store, so a restart mid-way keeps showing it as a pre-heat (0.8.2). The panel says Pre-heating, not Boosting, on the card's button, the boost sheet ("Stop pre-heating"), the device page and the Schedule tab; HA's own climate card still shows the boost preset. The climate entity has a `preheat` attribute while it runs, and `stats.sample_from_state` counts that as schedule, not boost. The panel's status carries `preheat` (`as_dict`) on heat; `hive_local/preheat {entry_id, enabled?, max_lead?}` goes through the switch and number so settings are restored. `frontend/src/Preheat.tsx` is the card on the heating Control tab; cards say "Pre-heating for 06:30". `tests/e2e/test_preheat_e2e.py` (mocked MQTT) covers it.
  - Holiday (issue #6): `holiday.py` (pure, unit-tested: `Away`, `restore_point`, `lease_minutes`, `needs_renewal`, `is_our_boost`, `judge` → KEEP / REASSERT / DROP) and `holiday_controller.Holiday` (`HiveData.holiday`, per receiver, all its channels). Heating is held with a **boost** at the holiday temperature (default: the frost protection number) as a fail-safe (Elliot, 2026-11-24): a boost is the receiver's only self-ending timer (a manual hold ignores the hold duration, see Key facts), so we boost for `min(6 h, time left)` and renew once an hour has run down (checked every 5 min); if HA stops, the receiver ends the boost within 6 h and goes back to its pre-boost mode, and in the last 6 h it ends exactly at `until`. Hot water is `off` (no fail-safe: a water boost means on). The end and cancel **restore the previous mode** (Elliot), taken from before any boost (`Transport.resume_state`). Stored in `.storage/hive_local.holiday.<entry_id>` (epoch `until`, temperature, restore mode/setpoint, `lease_end`). Reports: our boost → keep; a boost at another temperature (or any water boost) is someone's boost on top, and when it ends the holiday is put back; our boost ending before `lease_end` means someone changed the mode → drop for that channel; ending at/after `lease_end` (HA was down) → put back. A 30 s settle window follows our writes and startup, with a re-check when it ends (an unchanged report isn't re-sent). Overdue holidays end on the receiver's first report after start. `Holiday.is_holding` (our boost is running): the panel shows Away, not Boosting (`holiday.holding` in the status), `HiveData.async_set_target` and climate `set_temperature` change the holiday temperature, climate preset is `away` (clearing it cancels; setting it raises), and `stats.sample_from_state` counts preset `away` as manual. Pre-heat is blocked while heating is away (`Preheat.blocked`). Climate and water_heater carry `holiday_until`. `frontend/src/Holiday.tsx` is the "Away until…" sheet; cards say "Away until Sat 14:00" (`formatUntil` in `api.ts`); the device page has an End row; "Everything back to schedule" skips channels on holiday. `tests/e2e/test_holiday_e2e.py` (mocked MQTT, SLR2) covers it.
  - Rooms call for heat (issue #4): `demand.py` (pure, tested: `valve_reading`, `room_need`, `calling`, `decide` → IDLE / START / KEEP / STOP, `boost_setpoint`, `scheduled_now`, `minutes_until_off`, `lease_minutes`, `Run`) and `demand_controller.Demand` (`HiveData.demand`, heating only). Opt-in per receiver (`switch` `room_demand`, off by default) plus `room_demand_outside_schedule` (off: no requests in the schedule's 1 °C periods); numbers `room_demand_start` (0.5 °C below target), `room_demand_stop` (within 0.2 °C), `room_demand_min_on` / `min_off` (10 min; Elliot kept the minimum on even when a valve is turned down, 2026-11-26, to spare the boiler short cycles), all restored. Every minute it reads the rooms whose `receiver` is this entry straight from HA states (not `RoomManager.status()`): a valve counts if it isn't unavailable/off and its `last_reported` is within 60 min, heating = `hvac_action` heating or `pi_heating_demand` ≥ 10 %, counted only while the room is below its target (a valve turned down keeps reporting heating for minutes while it closes, which kept the boiler on: Elliot, 2026-11-26); while it's only waiting out the minimum on time, the boost isn't re-sent at a new temperature; a stale room sensor falls back to the valves; a room with nothing usable is ignored. It only starts from **Schedule** (never Off or Manual), when the receiver isn't already heating, with a **boost** (fail-safe, like the holiday) at max(scheduled + 2, receiver's reading + 1, the rooms' target), ≤ 32 °C, for a 30 min lease ending early at the schedule's next off (from pre-heat's cached schedule, read when it's turned on without a full week), renewed under 20 min left; when the rooms are warm (after min on) or the schedule turns off, it cancels the boost (`Transport.resume_state`, so back to the schedule). Ours = boosting at our setpoint; a 30 s settle window follows our writes. Someone cancelling it or changing the mode stops it until the rooms are warm (or Manual/Off → Schedule); someone's boost on top just ends the request. **Holiday and pre-heat win:** nothing while `holiday.away` has heating or `preheat.active_for` is set, and we step aside without cancelling; `Preheat.overridable` (= `Demand.owns_boost`) lets pre-heat start over our boost. Choosing Schedule while it runs does nothing (`HiveData.async_set_mode`). Stored in `.storage/hive_local.demand.<entry_id>` (`run`, `last_end`, `suppressed`; removed with the entry); after a restart our boost is picked up again, or released as lapsed if the receiver's back on schedule. Climate attribute `room_demand` (room names while running; `stats.sample_from_state` counts it as schedule), status `demand` (`as_dict`: enabled, outside_schedule, active, rooms, calling, setpoint, reason), `hive_local/demand {entry_id, enabled?, outside_schedule?}` (through the switches). The panel says "Heating for Bedroom" on the card, the device page and the Schedule tab, "For rooms" on the button, "Stop for now" in the sheet, Schedule stays selected, and "Everything back to schedule" leaves it alone; Settings has a "Rooms call for heat" row per receiver (On/Off, then Outside the schedule). `tests/e2e/test_demand_e2e.py` (mocked MQTT, OTR1, a fake ZHA valve) covers it.
  - Room boost (2026-11-26): boost one room for a while. `room_boost.py` (pure, tested: `check` 15 min–6 h and 5–32 °C, `start` keeps the valves' targets from before the first boost, `restore`, `Boost` with `remaining`/`over`) and `room_boost_controller.RoomBoosts` (house-wide, `hass.data[DATA_ROOM_BOOSTS]`, created in `async_setup`, stored in `.storage/hive_local.room_boost`): sets the room's valves to the boost temperature (`climate.set_temperature`), and when time's up (checked every 30 s, also after a restart) or it's stopped puts each valve's own target back, retrying a valve that's unavailable for up to 6 h (`pending`). The valves have no timer of their own, so they stay boosted while HA is down; the boiler doesn't. **Boiler (Elliot: yes, even with "Rooms call for heat" off):** each receiver's `Demand` treats a boosted room (`RoomBoosts.active_rooms`) as calling until within `stop_within` of the boost temperature, whether or not the switch is on, in the schedule's off periods and from Manual, with no minimum off; never while the heating is Off, and holiday and pre-heat still win. ## Key facts

- zigbee-herdsman-converters `hive.ts`: every SLR model includes `fz/tz.thermostat_weekly_schedule` and `tz.thermostat_clear_weekly_schedule`. They're just not in `exposes`.
- SLR2 is `multiEndpoint` with endpoints heat=5 and water=6, so keys are `weekly_schedule_heat` / `weekly_schedule_water` (and `system_mode_heat` etc.). SLR1/OTR1 use plain keys.
- Z2M's `get` for `weekly_schedule` sends `getWeeklySchedule` with `daystoreturn: 0xff, modetoreturn: 3`. Elliot's receiver accepts that, and also `127` / `1`.
- **Verified on Elliot's receiver (single-endpoint, plain `weekly_schedule`):** the reply arrives as one `commandGetWeeklyScheduleRsp` **per day**, all within about 1 s. Z2M publishes each one as `{"weekly_schedule": {"days": ["monday"], "transitions": [{"time": 390, "heating_setpoint": 20}, ...]}}` and always sends 6 transitions, padded with 1 °C entries. The padding repeats entries at the same time (e.g. 22:00 1 °C ×3), so both parsers run `schedule.tidy_transitions`, which keeps the first entry per time. Without it a re-read day showed duplicate events, and `validate()` rejected it on write-back. It also maps setpoints below 1 °C to 1 °C ("off"; the receiver can report 0 °C) and drops ones above 32 °C (logged), so a day read back can always be written back. In the Z2M log, Sunday didn't appear: check whether it's genuinely missing.
- Write payload: `{"weekly_schedule[_ep]": {"dayofweek": [...], "transitions": [{"heatSetpoint": 20, "transitionTime": "06:30"}]}}`. Z2M works out the mode and the number of transitions.
- **Always write 6 transitions per day** (0.8.4, `schedule.pad_transitions`, applied in `per_day`, so both transports get it). The receiver keeps 6 slots and a shorter write leaves the rest untouched, often uninitialised: Elliot's SLT3d showed `07:00 20° · 08:30 off · 16:30 20° · 19:00 off · 68:15 15° · 00:30` (4095 min = 0x0FFF). We pad by repeating the last transition, as the receiver does when it reports. Reads drop times outside 0–1439 (`schedule.valid_minutes`) rather than taking them modulo a day.
- Modes (Z2M SLR2b docs): schedule = `{"system_mode": "heat", "temperature_setpoint_hold": false}` (**not** `auto`); manual = `system_mode heat` + hold `1` + `occupied_heating_setpoint` (5–32); off = `system_mode off` + hold `0`. On water, manual means "always on" and has no setpoint (`occupied_heating_setpoint_water` is always 22).
- Boost must be **one** payload: `{"system_mode":"emergency_heating","temperature_setpoint_hold_duration":30,"temperature_setpoint_hold":1,"occupied_heating_setpoint":21}`. Water boost has no setpoint. Duration is 1–360 minutes, and `65535` means not used.
- "No reply" in the panel means zero days were collected. On Z2M that's almost always a wrong friendly name or base topic.

- **A manual hold ignores the hold duration (verified on Elliot's OTR1 over ZHA, 2026-11-24):** writing `system_mode heat`, `temp_setpoint_hold_duration 10`, `temp_setpoint_hold 1` and a setpoint in one Write Attributes is accepted, but the duration reads back 65535 straight away and the hold was still on after 14 min. Only a boost (`emergency_heating`) ends by itself, which is why the holiday holds with a boost.

### ZHA (zigpy 0.92 / zha 0.0.90, as pinned by HA 2026.2)

- zigpy's attribute names are `temp_setpoint_hold` (0x0023) and `temp_setpoint_hold_duration` (0x0024), not Z2M's `temperature_setpoint_hold*`. Temperatures are centi-°C.
- **Reading the schedule:** the receiver answers with one `get_weekly_schedule_response` per day, all with the request's TSN. With `expect_reply=True`, zigpy hands the first one to the request future and never shows it to listeners, so we send with `expect_reply=False` and collect every reply with a legacy `cluster.add_listener` (`cluster_command`). `tests/e2e/test_zha_e2e.py` fails if this is flipped back (the read comes back incomplete).
- **State:** we listen to the cluster's `attribute_read/report/updated/written` events and rebuild status from the attribute cache. ZHA configures reporting for `system_mode`, `occupied_heating_setpoint`, `local_temperature` and `running_state`, but **not** the hold attributes. So we read all state on start and every 5 min, re-read the hold attributes 3 s after a reported mode or setpoint change (and after each of our writes), and poll while boosting.
- Modes and boost are one `write_attributes` call, in the same field order as the Z2M payload.
- **Thermostat reporting fix (`_ThermostatReporting` in `transports/zha.py`):** ZHA configures a Hive SLT's temperature (0x0402) reporting as 30 s / 900 s / 0.5 °C, and the receiver drops a thermostat it hasn't heard from in a few minutes: red light, boiler off, "No signal", about every 6 min (zigpy/zha-device-handlers#2776, fixed there with zha_toolkit `conf_report` 5/120/50 on endpoint 9). We find SLT thermostats (`zcl.is_hive_thermostat`) in the ZHA gateway, and on each temperature report (it's awake) call `configure_reporting("measured_value", 5, 120, 50)` until it's accepted, then again after `THERMOSTAT_REPORTING_REFRESH` (24 h). One watcher per thermostat across entries (`hass.data[THERMOSTATS_WATCHED]`). Reported on Elliot's OTR1 + SLT3d after moving to ZHA. `configure_reporting` returns a list of records in zigpy 0.x but `{ZCLAttributeDef: Status}` in zigpy 2.x (HA 2026.11), so check it with `zcl.reporting_accepted` (issue #1). `write_attributes` still returns `[[records]]` in 2.4.1. `tests/e2e/test_thermostat_reporting_e2e.py` (real zigpy `TemperatureMeasurement` cluster, fake radio answering like an SLT6b) passed on HA 2026.11.2 / zigpy 2.4.1 and HA 2026.2.3 / zigpy 0.92 when written; v0.3.4 fails it on 2.4.1 with the issue's traceback.
- **Channels come from the model, like Z2M:** SLR1* / OTR1 are heating only (endpoint 5), SLR2* are heating 5 + hot water 6, and unknown models go by which endpoints have a Thermostat cluster (`zcl.receiver_endpoints`). A single-channel receiver on ZHA was reported showing hot water, so it probably lists a Thermostat cluster on endpoint 6 too.
- Z2M's definitions give every Hive receiver `meta: {disableDefaultResponse: true}`, so `set_weekly_schedule` is sent the same way (`disable_default_response=True, expect_reply=False`). Errors only show up when the schedule is read back.
- If the ZHA integration reloads, it rebuilds its devices and our cluster references go stale. `ZHATransport.check_device()` re-resolves them every minute (see Repairs, #13); not yet tried against a real ZHA reload.

Rooms carry `sensor_on_valves` (default true, kept when a save leaves it out); valves carry `external_sensor` (`using`/`waiting`/`unsupported`/`off`), `external_sensor_sent`/`_reported`, `radiator_covered`; rooms `external_sensor` (also `partly`). The panel shows it under the temperature in `RoomSheet` and as "Use the room sensor on the valves" in the editor. Diagnostics carry `valve_sensors`. The valve's onboard weekly schedule is in too (#5; see Layout → Valve schedules).
3. ~~**Boiler demand (opt-in)**~~ Done (issue #4, "Rooms call for heat"; see Layout): when a room is below target (or a valve heating) and the receiver isn't, boost the heating in 30 min leases; otherwise leave it on its own schedule. Fails safe: the boost ends by itself if HA stops. Not yet tried on real valves.

- **Shipping an update (release-please, from 0.10.0):** don't bump versions or write notes by hand. Merge PRs to main (squash-merge only, titled as a conventional commit, which `commits.yml` checks). `.github/workflows/release-please.yml` keeps one open release PR, `chore(release): x.y.z`, with the version bump (`version.txt`, `.release-please-manifest.json` and `manifest.json` via `extra-files`) and `CHANGELOG.md`, its notes grouped from the commits since the last release (`feat` → New, `fix` → Fixed, `perf`, `revert`; docs/ci/chore/refactor/test/style/build hidden). Below 1.0 a `feat` bumps the minor and a `fix` the patch. Merging the release PR tags it and publishes the GitHub release (the Marketplace (formerly HACS) offers releases as updates; without one, **Update** stays greyed out). Config: `release-please-config.json`. **`last-release-sha` is set to `daafe04` (the squashed 0.9.0 commit, since the v0.9.0 tag points at a commit no longer on main): remove it from the config once 0.10.0 is released**, or every later release PR will count from 0.9.0. It uses the built-in token, so the release PR is by github-actions[bot], not Elliot (his choice over a personal token or a GitHub App, 2026-11-24). Changes made with that token don't trigger `pull_request` workflows, so after creating or updating the release PR `release-please.yml` starts them by hand (workflow_dispatch, which that token may do): `validate.yml` on the release branch, `commits.yml` with the PR's title and base as inputs, and `prerelease.yml` (with the PR number) when the PR has the `pre-release` label. Their check runs land on the branch's head commit, so they show on the PR. The repo setting "Allow GitHub Actions to create and approve pull requests" must be on. **Pre-releases:** add the `pre-release` label to the release PR (adding it triggers `prerelease.yml` directly, since a person does it); `.github/workflows/prerelease.yml` publishes that version as a GitHub pre-release from the PR's head with the PR's notes, and republishes it on every later push (a pre-release of the same version is deleted with its tag and recreated; a full release is never touched). Testers **Redownload** it, as the version number doesn't change. **Any other PR** can be labelled too (2026-11-24: labelling feature PR #28 did nothing, since only release PRs bump the version and v0.9.0 was already released): it's published as the version it would lead to plus `-beta.<PR>` (from the PR title: `feat` → next minor below 1.0, `!` → next minor, anything else → next patch; e.g. `v0.10.0-beta.28`), tagged on a commit the workflow makes off any branch with that version in manifest.json. Closing the PR or removing the label deletes it. When the release PR merges, `release-please.yml` deletes that pre-release first so release-please can publish the real one under the same tag. Notes for 0.4.0–0.9.0 are in `docs/releases/` (no longer written); `release.yml` is gone. Cloud sessions can't push tags (the git proxy returns 403) or create releases (the API returns 403), which is why it all goes through workflows.
